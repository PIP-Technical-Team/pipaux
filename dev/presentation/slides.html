The Big Picture

What is the pipeline responsible for? How is it built?

One main orchestrator - {pipaux}

An R package that manages the 20+ auxiliary measures that feed the World Bank’s global poverty estimates. For example, price data, national accounts, demographics and poverty measurement parameters.

Takes raw data from different sources, cleans, validates, and formats each one into ready-to-use datasets for PIP’s poverty estimates.

End-to-End Workflow

How data moves from source to published artifact — eight stages

Pipeline Stages

Key principle — skip logic is as important as the update logic.

The system only does work when something actually changed. A typical run where no sources have changed completes with every measure skipped — zero writes, full auditability.

What flows between stages:

  • S1 → S2: raw file SHA from GH
  • S2 → S3: update_gh / update_y flags
  • S3 → S4: ordered dependency list
  • S4 → S5: raw data + attributes(x)$gh
  • S5 → S6: validated data + metadata
  • S6 → S8: versioned artifact + sidecar

Reproducibility Through the Pipeline

Every artifact on the Y-drive carries a sidecar — a companion metadata file that makes it self-describing.

measure.qs2          ← the data
measure.qs2.sidecar  ← the provenance record

Sidecar contains:
  gh:
    owner:      "PIP-Technical-Team"
    repo:       "aux_cpi"
    branch:     "20260202_PROD"
    file_path:  "InputData/cpi.csv"
    gh_raw_sha: "a3f8c2..."     ← GH file fingerprint

  code_hash:  "d9e1b7..."       ← aux_cpi() body hash
  code_label: "aux_cpi"        ← function name
  pk:         ["country_code", "year"]

Two questions you can always answer:

“What raw data version produced this file?”

→ Compare gh_raw_sha against current GitHub SHA

“Did the formatting logic change since this was saved?”

→ Compare code_hash against hash_code(aux_cpi)

Both comparisons happen automatically on every run — triggering updates only when needed.

The Orchestration Engine

aux_fun() and update_aux_measures() — the central coordinators

Two Entry Points

aux_fun() — single measure

aux_fun(
  measure = "cpi",
  verbose = TRUE
)
  • Resolves dependencies recursively
  • Checks GH + Y-drive status
  • Executes only what’s needed
  • Initialises + finalises the audit log when called from the top level

Use when: updating one measure interactively, or running a targeted update.

update_aux_measures() — batch

update_aux_measures(
  measures = c("cpi", "gdp"),
  log      = TRUE,
  log_save = TRUE
)
  • Reads dependency manifest
  • Preserves topological order
  • Shares a single processed environment across all measures
  • Prevents double-processing of shared dependencies

Use when: running a full release update.

How the Engine Decides: Three Signals

Before any data is written, three checks run in sequence:

① GitHub Branch Sync

Is the release branch on the aux_* repo in sync with DEV?

check_github_status(
  measure        = "cpi",
  repo           = "aux_cpi",
  release_branch = "20260202_PROD"
)

If branch is missing or behind DEV → sync it.

Policy: GH update always implies Y-drive update.

② GitHub SHA Comparison

Does the raw file SHA stored in the Y-drive sidecar match the current SHA on GitHub?

# Inside check_y_drive_status()
gh_sha <- get_file_info_from_gh(
  owner, repo, branch, file_path
)$sha

y_sha <- sidecar$gh$gh_raw_sha

sha_mismatch <- gh_sha != y_sha

Any mismatch → re-run the formatter.

③ Code Hash Comparison

Did the aux_*() function body change since the last save?

# Inside check_y_drive_status()
fun     <- get(sidecar$code_label)
fun_sha <- hash_code(fun)

fun_changed <-
  fun_sha != sidecar$code_hash

Any mismatch → re-run, re-save.

This catches silent logic changes even when raw data is unchanged.

The Decision Matrix

GH branch status SHA match Code hash match Action
Missing / behind DEV — — Sync GH → update Y-drive
In sync ✗ mismatch — Update Y-drive
In sync ✓ match ✗ mismatch Update Y-drive
In sync ✓ match ✓ match Skip — nothing to do
Skipped (countries, missing_data) ✓ match ✓ match Skip
Sidecar missing — — Update Y-drive

Note

The skip case is the common case. In a stable release where no sources changed and no formatter functions were modified, every measure in the pipeline completes with zero writes.

Dependency Graph

How measures relate, and how the graph drives execution order

Why the Graph Shape Matters

Hubs and cascades

country_list is upstream of most measures. A single change there propagates automatically to regions, countries, censoring, metadata, gdm, gdp, and missing_data.

pfw is the second hub: it feeds countries, metadata, gdm, and missing_data.

gdp is the most complex derived measure: assembled from six raw sources (WDI, WEO, Maddison, SNA, NAN, POP) plus country_list.

missing_data sits at the bottom — it depends on nearly every other measure and is always updated last.

What the algorithm guarantees:

  • No measure is processed before its dependencies
  • No measure is processed twice (the processed environment acts as a visited-node set)
  • A failure in a dependency is logged and controlled by halt_on_dep_fail
# Inspect the live dependency graph
deps <- read_dependencies(
  gh_user = "https://raw.githubusercontent.com",
  owner   = "PIP-Technical-Team"
)

# Visualise it
plot_dependencies(deps)

Execution Order Algorithm

update_aux_measures() resolves order before starting any work:

# 1. Read manifest (dependency-ordered list)
available_measures <- names(
  read_dependencies(
    gh_user = "https://raw.githubusercontent.com",
    owner   = "PIP-Technical-Team"
  )
)

# 2. Subset to requested measures,
#    preserving manifest order
final_measures <- available_measures[
  available_measures %in% measures
]

# 3. Shared processed environment
processed <- new.env(parent = emptyenv())

# 4. Loop — each call to aux_fun() marks
#    its own dependencies as processed
for (measure in final_measures) {
  aux_fun(measure, processed = processed, ...)
}

Why a shared processed environment?

When you request c("cpi", "gdp"):

  • Both depend on country_list
  • Without a shared visited-node set, country_list would be checked (and potentially updated) twice
  • The processed env is passed by reference into every recursive aux_fun() call
  • Once country_list is marked, all subsequent measures skip it immediately

This is the mechanism that prevents duplicate work across a batch run.

Recursive Update Workflow

A detailed look at what happens inside a single aux_fun() call

The Full Algorithm

What the Y-Drive Update Actually Does

When update_y = TRUE, execute_update() calls the measure’s generator function:

# Dynamically resolve the function
func_name <- paste0("aux_", measure)
func <- get(func_name,
            envir = asNamespace("pipaux"))

# Build args — only pass what the
# function actually accepts
update_args <- list(
  action = "update",
  branch = release_branch,
  owner  = owner,
  tag    = tag,
  repo   = repo
)

filtered_args <- update_args[
  names(update_args) %in%
    names(formals(func))
]

do.call(func, filtered_args)

Inside each aux_*() function:

  1. pipfun::load_from_gh(...) — fetch raw data, captures attributes(x)$gh
  2. *_validate_raw(x) — validate incoming structure
  3. Format / clean / join
  4. *_validate_output(x) — validate result
  5. pip_aux_save(x, metadata = list(gh = ...), code = ..., pk = ...) — write to Y-drive with full provenance

The critical invariant:
attributes(x)$gh must be present on everything that flows into pip_aux_save(). This is what enables SHA-based change detection on the next run.

Handling Derived Measures

Some measures don’t read from GitHub directly — they are computed from other aux data:

Example: aux_countries

# Load from already-updated measures
cl  <- pipload::load_aux_data("country_list")
pfw <- pipload::load_aux_data("pfw")

# Subset: countries in pfw with inpovcal == 1
result <- cl[
  country_code %in%
    pfw[inpovcal == 1, country_code]
]

# Aggregate GH metadata from inputs
combined_gh <- list(
  attributes(cl)$gh,
  attributes(pfw)$gh
)

pip_aux_save(result,
  metadata   = list(gh = combined_gh),
  code       = aux_countries,
  code_label = "aux_countries",
  pk         = "country_code"
)

Change detection for derived measures:

Since there is no single raw file, change detection relies on:

  • Code hash: if aux_countries() body changes → re-run
  • Inherited GH SHAs: combined_gh carries the original raw file SHAs from country_list and pfw

On the next run, check_y_drive_status() iterates over every entry in sidecar$gh and compares each against its current GitHub SHA.

If country_list was updated upstream, its SHA changed → aux_countries detects the mismatch and re-runs automatically — even though it never reads directly from GitHub.

This is the cascade mechanism.

Supporting Infrastructure

Versioning · Logging · Comparison tools

Versioning with stamp

{pipaux} uses the stamp package for content-aware artifact versioning.

Three modes:

# Default — new version only when
# content or code changes
pipaux_set_versioning("content")

# Force new version every run
# (useful for debugging)
pipaux_set_versioning("timestamp")

# Overwrite in place, no history
pipaux_set_versioning("off")

pipaux defaults (pipaux_reset_stamp_options()):

  • versioning = "content"
  • retain_versions = Inf
  • force_on_code_change = TRUE
  • code_hash = TRUE

What content-based versioning means in practice:

Each time pip_aux_save() is called, stamp computes a hash of the data. If the hash matches the current stored version, no new version is created.

Versions are stored under:

Y:/PIP_ingestion_pipeline_v2/
  20260202_PROD/
    aux_data/
      cpi.qs2              ← current
      cpi.qs2.sidecar      ← current provenance
      cpi.qs2/
        versions/
          v1_20260115/     ← prior version
          v2_20260202/     ← this version

Within a release, you can always roll back or compare vintages without touching the main file.

Logging Framework

Every run produces a structured audit trail.

Log lifecycle:

  1. init_aux_log() — called at top-level entry
  2. log_add(event, message, logmeta) — called at each step
  3. finalize_aux_log() — called on exit via on.exit()
  4. Optionally: pipfun::log_save() persists to Y-drive

Accessing logs:

# Quick summary table
aux_log_summary()
#      measure   status
# 1:       cpi  success
# 2:       ppp  success
# 3:       gdp    error

# Full structured log
aux_log_last()

# Load a saved log from disk
pipfun::log_load(
  id    = aux_log_last_name(),
  alias = get_from_auxenv("aux_meta_alias")
)

Each log entry captures:

→ [2026-05-28 13:59:18] INFO
  message:  "Starting status check for: cpi"
  step:     "START"
  measure:  "cpi"

→ [2026-05-28 14:01:42] UPDATE
  message:  "Updated Y drive for: cpi"
  step:     "UPDATE_Y"
  measure:  "cpi"

→ [2026-05-28 14:01:45] SUCCESS
  message:  "Measure and dependencies
             successfully updated"
  step:     "END"
  measure:  "cpi"

Log steps: START → UPDATE_GH → UPDATE_Y → END
Error steps: ERROR_CHECK · ERROR_GH · ERROR_Y · ERROR_DEP

Comparison Tools

After updating, two functions let you inspect what changed.

compare_aux_releases()

“What changed between this release and last?”

changes <- compare_aux_releases(
  measure     = c("cpi", "gdp"),
  old_release = "20260101_PROD"
)

# Cell-level differences
changes$cpi$diff_values
# Rows added / removed
changes$cpi$diff_rows

Compares the current release’s .qs2 artifact against the most recent previous release of the same identity.

Automatically detects old_release if not supplied.

compare_aux_vintages()

“Did my re-run within this release change anything?”

vintage_changes <- compare_aux_vintages(
  measures = c("cpi", "gdp"),
  version  = -1   # vs immediately prior version
)

Compares version N against version N + version within the same release directory.

Both return:

Field Contents
diff_values Cell-level diffs (.x = new, .y = old)
diff_rows Added / removed rows with change_type

Attributes carry: key_cols, release, old_release, new_path, old_path.

Quick Start

The complete workflow in four commands

Full Workflow

# ── 1. Initialise the runtime environment ─────────────────────────────
pipfun::setup_working_release(release = "20260601", identity = "TEST")
devtools::load_all()

# Verify
get_from_auxenv("wrk_release")
#> $release   "20260601"
#> $identity  "TEST"

# ── 2. Update measures (dependencies resolved automatically) ──────────
update_aux_measures(
  measures = c("cpi", "ppp", "gdp"),
  owner    = "RossanaTat",   # use personal fork for testing
  log      = TRUE,
  log_save = TRUE
)
# ✔ No updates needed         ← common case when nothing changed
# ✔ Updated GitHub for: cpi   ← when release branch was behind DEV
# ✔ Updated Y drive for: cpi  ← when SHA or code hash differed

# ── 3. Inspect the audit log ──────────────────────────────────────────
aux_log_summary()

# ── 4. Verify nothing unexpectedly changed ────────────────────────────
compare_aux_releases(measure = c("cpi", "gdp"))

Tip

Always call pipfun::setup_working_release() before any update or read operation. It populates the .pipaux runtime environment with paths, release metadata, and options.

Checking Status Without Updating

When you want to understand the current state without triggering any writes:

# Full status check with reasons
check_status("maddison", include_reason = TRUE)

# ── Checking Status for maddison ────────────────────────────────────
# ✔ GitHub branch 20260601_TEST is up to date with DEV.
# ✔ Current and stored function SHAs match.
# ── Summary ─────────────────────────────────────────────────────────
# ℹ Update GitHub: FALSE
# ℹ Update Y drive: FALSE
# Or use the quiet wrapper for programmatic use
status <- get_fs_status("cpi", include_reason = TRUE)
status$update_y    #> TRUE
status$y_reason    #> "Y drive out of sync"

check_status() and get_fs_status() are used internally by aux_fun() — but they are also useful standalone diagnostic tools when you need to understand why a measure is (or isn’t) being updated.

Summary

What {pipaux} Does

System capabilities:

  • Manages 20+ auxiliary measures with a single call
  • Resolves dependency order automatically from a manifest
  • Detects changes via three independent signals (GH branch, file SHA, code hash)
  • Saves every artifact with full provenance (sidecar)
  • Versions content — writes only when something changed
  • Produces structured audit logs for every run
  • Compares releases and vintages to surface what changed

Architecture:

aux_fun() → process_dependencies() → get_fs_status() → execute_update() → pip_aux_save()

Three key design principles:

Tip

Fail loudly — explicit errors for missing data, sidecar, or GH artifacts. No silent fallbacks.

Note

Commit provenance — attributes(x)$gh must survive through the entire pipeline from load to save.

Warning

Dependency-first — all upstream measures are resolved and marked processed before a measure updates itself.

update_aux_measures()

One call. All dependencies. Full provenance. Complete audit trail.
